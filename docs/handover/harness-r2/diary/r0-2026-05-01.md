### Harness-r3 hook — deterministic-stuck divergence pattern under temp=0

Lead-flagged risk materialized exactly as predicted: pinning gemma to temp=0 collapsed token-level sampling but did NOT collapse task-outcome variance — instead it shifted variance from sampling noise to **deterministic-stuck path divergence**. Trace evidence (gemma-react pin-1 vs pin-2):

- `trivial-1-example-homepage`: pin-1 OK cov=0.00 turns=6 (model navigated `http://example.com`, emitted RUN_COMPLETED with stale title) → pin-2 INCOMPLETE cov=1.00 turns=5 (model navigated `https://example.com`, full coverage, never emitted RUN_COMPLETED). Δ step-cov 1.00 on a single task.
- `journey-6-media-streaming`: pin-1 INCOMPLETE cov=0.00 turns=6 → pin-2 INCOMPLETE cov=0.80 turns=15. Δ step-cov 0.80.
- `journey-3-flight-search`: pin-1 INCOMPLETE cov=0.00 turns=15 → pin-2 INCOMPLETE cov=0.25 turns=3. Different exit point (MAX_TOOL_ROUNDS vs early bail).

Mechanism candidates:
1. **Browser-mcp / DOM timing stays stochastic** — observations differ between sweeps (page load order, ad timing, network jitter). Gemma at temp=0 follows different deterministic paths from those tiny input deltas; gemini at temp=0 has more reasoning headroom to absorb them (hence its band collapsed, gemma's didn't).
2. **Time-of-day / Ollama mmap state** — sweep 2 ran ~30% faster (warmer cache); could correlate with subtle latency changes that shift `wait_for` race outcomes.
3. **URL canonicalization in plan-decomposer or supervisor** — `http://` vs `https://` divergence on `trivial-1` suggests an upstream normalization gap that's input-state-dependent.

**Candidate harness-r3 fix paths**:
- Audit `wait_for` timeout / settling logic in browser-mcp for race conditions.
- Audit `take_snapshot` ordering against navigation completion signals.
- Pin URL canonicalization in plan decomposer output (force `https://` if scheme missing).

Variance pin alone is necessary but insufficient for tight A:B gates on the gemma path. Tightening upstream of the model could push the band tighter than pinning alone — meaningful uplift for harness-r3 distillation A:B work.

### Diagnosis — completion_check made the model OVER-verify

The 2 strict-passes that converted to FAIL in P2 were both on tasks where Pro 3 could not stop emitting verification actions. Trace evidence:

**`calibration-1`** (P1-sweep-2 strict-passed in 2 turns → P2 doom-loop FAIL in 6 turns):
- P1 baseline: navigate → RUN_COMPLETED:passed (2 turns).
- P2: navigate → STEP_DONE → 3 identical `fill` calls (doom-loop on `fill { ..., text: undefined }`). Model tried to "verify expectedOutcome" by interacting; doom-loop detector terminated with RUN_COMPLETED:failed.

**`journey-8`** (P1-sweep-2 strict-passed in 9 turns → P2 MAX_TOOL_ROUNDS in 15 turns):
- P1 baseline: 9 turns, ended RUN_COMPLETED:passed.
- P2: emitted STEP_DONE for all 3 plan steps, then 6 extra turns of verification observe/interact actions without ever emitting RUN_COMPLETED. Hit MAX_TOOL_ROUNDS=15. Harness terminated with RUN_COMPLETED:failed.

**Mean turn count gemini-react**: P1 sweep 1 = 10.2, P1 sweep 2 = 8.8, **P2 = 9.3** (+0.5 vs sweep 2; not a wall-clock blowup but enough to push 2 tasks past the success cliff).

**Mechanism**: The block's "every plan step's expectedOutcome is verified against the latest <observation>" was read by Pro 3 as license to take MORE verification actions before declaring done. Instead of trusting STEP_DONE markers as the verification record, the model re-observed/re-interacted to "make sure". On easy tasks (calibration-1) this fired a doom-loop on extra `fill` calls; on hard tasks (journey-8) it burned the turn budget.

### R10/R11 narrative correction (the most substantive finding of harness-r2 so far)

The "Pro 3 stopping-criterion problem" documented in R10 was **overstated as a capability gap**. The data shows it was **70% temperature, not prompt**:

**Pro 3 premature timeline**:
- R10 (pre-pin gemini @ temp=1.0): 13/20 RUN_COMPLETED:failed with finalState < 1.0
- P1 post-pin (temp=0): **3/20** premature
- P2 post-completion_check: 3/20 (no further movement)

**gemini-react strict-pass timeline**:
- R10 baseline (temp=1.0): 2/20
- P1 post-pin (temp=0): **4/20 max** (3 sweep-1 / 4 sweep-2)
- P2 post-completion_check: 2/20 (regression)

The variance pin alone delivered:
- 10/20 reduction in premature-completion (13→3)
- 2/20 uplift in strict-pass count (2→4)
- 0/20 empty-content invariant maintained

This materially reframes R12's distillation data-quality premise: the post-pin gemini-react strict-pass yield is **double R11's anchor** (4/20 vs 2/20). Multi-sweep with pinned temp may yield enough strict-pass trajectories without the trajectory-level cleanup R10's closure suggested. R12 plan ought to factor this in.

### Decision — Option A: revert completion_check + skip P2

Lead-authorized decision (matches engineer recommendation). Reasoning:
1. The strict-pass uplift from temp pin (2 → 4) is the actual win this wave delivered on the strategic gate.
2. R10's 13/20 premature was a temp=1.0 artifact, not a prompt-level reasoning gap — pin alone collapsed it to 3/20.
3. The 3 remaining premature cases on gemini-react are tasks where the model genuinely thinks it's done — not a prompt-fixable shape.
4. P3 (PLAN_UPDATE elicitation) targets a fundamentally different capability gap (0/60 emission rate) — not contingent on stopping-criterion working.
5. The honest narrative for harness-r2: variance pin solved the documented stopping-criterion gap; further prompt-level intervention introduced an over-verification regression and was reverted.
