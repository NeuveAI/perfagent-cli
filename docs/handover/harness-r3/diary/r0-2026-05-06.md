**Detector design** (`packages/local-agent/src/tool-loop.ts`):

- Constants colocated with `DOOM_LOOP_THRESHOLD = 3`:
  - `REFLECT_INJECTION_THRESHOLD = 2` (strictly less than doom-loop so injection precedes abort)
  - `REFLECT_DIRECTIVE_TEXT` (single-source string; same wording in
    chunk-update + observation prefix)
- New `RejectionFingerprint` interface `{ stepId, shapeHash, kind: "parse-fail" | "tool-error" }`.
- `recentRejections[]` sliding window capped at `DOOM_LOOP_THRESHOLD`. Streak
  resets when shape changes, on PLAN_UPDATE / STEP_DONE (forward progress),
  or on a successful (non-error) tool call.
- `lastSeenStepId` tracks the most-recent envelope's `stepId` so a
  parse-fail with no extractable stepId attributes the rejection to the
  step being worked on.
- Critical behavioral change at the parse-failure branch (`tool-loop.ts:208`):
  pre-r3 the loop aborted on the first `SchemaError` ("non-schema-valid
  agent output. Aborting run."); post-r3 the loop:
  1. Feeds the parse failure back as `<observation>(parse failure: ...)</observation>`
  2. Tracks the rejection under `stepId + shapeHash` (200-char normalized
     prefix of envelope content)
  3. On the **second same-shape parse-fail** prepends a `<observation>REFLECT: ...</observation>`
     to the next observation message AND surfaces a UI chunk
     `[Local agent: REFLECT: ...]`
  4. On the **third same-shape parse-fail** aborts via the existing
     doom-loop seam with a refreshed message: `non-schema-valid agent
     output 3× in a row. Aborting run.`

**Tool-error path** (Action envelope parses, but `mcpBridge.callTool`
returns `isError=true`):

- `shapeHash = "tool:" + functionName + ":" + argsHash` so two consecutive
  same-tool+same-args rejections collapse into a single streak.
- Existing doom-loop detector (3 identical consecutive ACTION envelopes)
  unchanged. The new `REFLECT_INJECTION_THRESHOLD=2` fires one step
  earlier and prepends the directive to the observation; the doom-loop
  abort still fires at threshold=3 if the model can't recover.

### Substantive findings beyond gate verdicts

1. **First PLAN_UPDATE emission in the harness-rN sequence**: 1/60 in
   wave-harness-r3-reflect-injection (calibration-5) vs 0/240 across 4
   harness-r2 sweeps. The structural injection moved the rate from
   floor to nonzero — directly validates the harness-r2 P3 finding
   that prompt-only intervention couldn't move the rate. The model is
   capable of emitting PLAN_UPDATE under the right harness-injected
   context.

   **Mechanism-validation trace excerpt** (verbatim from
   `packages/evals/evals/traces/wave-harness-r3-reflect-injection/gemma-react__calibration-5-three-step-search.ndjson`,
   the canonical reviewer artifact for finding #1):

   ```
   turn 2: agent_message "The previous action failed because the `interact` tool was called with a URL directly in the `args` object, which is not the correct schema for the `navigate` command."
   turn 3: agent_message "The previous two attempts to navigate using `interact` failed with the same `SchemaError`, indicating that the tool call structure is incorrect for the `navigate` command..."
   turn 4: agent_message "The repeated schema errors suggest a fundamental misunderstanding..."
   turn 5: agent_message "The environment is repeatedly failing to parse the `interact` tool call for navigation, regardless of how I structure the `args` object..."
   turn 6: agent_message "[Local agent: REFLECT: This step is failing in the same shape twice in a row. The next envelope MUST be PLAN_UPDATE with action=insert (missing prerequisite step), action=replace (corrected step), or action=remove (now-redundant step). Do not retry the same ACTION.]"
   turn 7: agent_message "The `REFLECT` directive has been triggered because the `interact` tool call for navigation failed twice in a row. I must now use `PLAN_UPDATE` to correct the plan.    turn 7: plan_update {action: "remove", stepId: ""}
   ```

   Trace shows: model reasons through repeated SchemaErrors → harness
   injects REFLECT → model's THOUGHT explicitly references the
   directive ("The `REFLECT` directive has been triggered ... I must
   now use `PLAN_UPDATE`") → model emits the PLAN_UPDATE envelope.
   This is the cleanest possible mechanism validation: the directive
   is being read, parsed, and acted on by the same model that emits
   0/240 PLAN_UPDATEs without it.

2. **Schema-invalid 5/20 floor → 0/20** is a **measurement-shift
   artifact, not a model-behavior change**:
   - **Pre-r3 schema-invalid metric definition**: tasks where the
     local-agent emitted the `[Local agent: non-schema-valid agent
     output. Aborting]` chunk. Pre-r3 this fired on the first parse
     failure (immediate abort).
   - **Post-r3 metric definition (legacy compatible)**: tasks where
     the local-agent emitted any `non-schema-valid agent output`
     chunk. Post-r3 this fires only on the 3rd consecutive same-shape
     parse failure (after REFLECT injection at threshold=2 doesn't
     recover). With model-stochasticity-residual + the new
     observation-feedback loop, the model rarely produces 3 identical
     parse failures in a row.
   - **Structurally-equivalent metric**: tasks that hit any parse
     failure at all = REFLECT-injection rate (lower bound) ≈ 7/60.
     Pre-r3 those 7 tasks would have aborted on the first parse fail,
     contributing to the schema-invalid count; post-r3 they recover
     into observation feedback + REFLECT (some emit PLAN_UPDATE
     thereafter; most ignore-and-retry or surrender).
   - **Headline framing**: the 5/20 → 0/20 is NOT model-quality
     improvement. It's the structural recovery pathway re-routing
     parse failures away from the abort chunk. The model still
     produces approximately the same parse-failure rate as pre-r3;
     the harness now catches and recovers instead of bailing.

   This nuance matters for harness-r4 sequencing: don't claim "P1
   eliminated schema-invalid output" — claim "P1 eliminated abort-on-
   first-parse-fail; the equivalent legacy metric is now REFLECT-
   injection rate".

3. **journey-1-bmw structural improvement (the canonical anchor)**:
   the BMW pattern (`interact{uid:"1_182"}` no command discriminator
   → SchemaError → abort) DID NOT RECUR in this sweep. The model
   produced parseable envelopes throughout, dismissed the cookie
   banner via legitimate `interact{command:"click", uid}` calls, and
   continued into the configurator flow. Either the prompt complement
   shifted the model's emission distribution OR temp=0 sampling
   residual happened to land on a different cliff edge. Distinguishing
   these would require a 2nd sweep (out of scope this wave). The
   net is the canonical fixture trajectory is materially better than
   harness-r2 pin-2.

4. **Capability gap is "post-REFLECT response strategy"**: model
   acknowledges the directive but defaults to surrender or retry
   instead of corrected PLAN_UPDATE. Calibration-5's `action=remove`
   was the only PLAN_UPDATE emission and it was the surrender shape
   (delete the failing step) not the recovery shape (insert a
   prerequisite or replace with corrected args). This is the
   capability gap P3's oracle-plan autopsy is sized to characterize.

### Harness-r4 candidate (from P2): THOUGHT-only loop detector

**Trigger condition**: track consecutive THOUGHT envelopes on the same
`stepId` without an intervening ACTION / STEP_DONE / PLAN_UPDATE
envelope. Reset on any non-THOUGHT envelope, on stepId change, or on
RUN_COMPLETED.

**Proposed thresholds** (symmetric with the existing detector ladder
`REFLECT_INJECTION_THRESHOLD = 2` < `DOOM_LOOP_THRESHOLD = 3`):

- `THOUGHT_REFLECT_THRESHOLD = 5` — after 5 consecutive same-stepId
  THOUGHTs, inject `<observation>The plan is stuck in deliberation.
  Emit ACTION (try the next concrete tool call) or PLAN_UPDATE (revise
  the step). Continued THOUGHT-only output for one more turn will
  abort.</observation>` into the next observation, AND surface a UI
  chunk `[Local agent: thought-only loop detected — emit ACTION or
  PLAN_UPDATE]`.
- `THOUGHT_LOOP_ABORT_THRESHOLD = 6` — after 6 consecutive same-stepId
  THOUGHTs without recovery, abort via the existing doom-loop seam
  ("Aborting to avoid wasted cycles"). Bounded at 6 to preserve

#### Incidence script (archived inline for reproducibility)

```bash
# THOUGHT-only loop incidence: count tasks where ≥ 5 consecutive turns
# produced agent_message events only (no tool_call between them) on the
# same stepId. Run from repo root.
for sweep in pin-1 pin-2; do
  for runner in gemma-react gemini-react gemma-oracle-plan; do
    dir="packages/evals/evals/traces/wave-harness-r2-$sweep"
    for f in "$dir"/${runner}__*.ndjson; do
      [ -f "$f" ] || continue
      task=$(basename "$f" .ndjson)
      runlen=$(python3 -c "
import json
turns_with_tool = set()
agent_message_turns = set()
with open('$f') as h:
    for line in h:
        try: ev = json.loads(line)
        except Exception: continue
        t = ev.get('turn')
        if t is None: continue
        if ev.get('type') == 'tool_call': turns_with_tool.add(t)
        elif ev.get('type') == 'agent_message': agent_message_turns.add(t)
turns = sorted(set(agent_message_turns) | set(turns_with_tool))
maxrun = 0
cur = 0
for t in turns:
    if t in agent_message_turns and t not in turns_with_tool:
        cur += 1
        if cur > maxrun: maxrun = cur
    else:
        cur = 0
print(maxrun)
")
      if [ "$runlen" -ge 5 ]; then
        echo "$sweep $runner $task max-thought-run=$runlen"
      fi
    done
  done
done
```

with no tool_call in same turn". For a precise harness-r4 implementation
the detector would track `stepId` from the last-seen envelope (the way
P1's `lastSeenStepId` does) rather than turn-bookkeeping in the trace.
The incidence rate is robust to this approximation because gemma's
THOUGHT-loops happen within a single stepId in practice (the model
doesn't bounce between steps mid-loop) — verified by spot-check of

### Thread 3 — Pro 3 plan quality on gemma-oracle-plan failures

Sampled 4 oracle-plan traces:

| Task | step-cov | Trajectory shape |
|---|---|---|
| `calibration-1-single-nav-python-docs` | 0.00 | 5 turns of THOUGHT-only output ("the tool keeps rejecting") with no successful tool_call event in the trace. **0 REFLECT** despite 5+ parse-fails. |
| `trivial-1-example-homepage` | 0.00 | navigate ✓ → snapshot ✓ → 2 same-shape `observe.evaluate` parse-fails → REFLECT → RUN_COMPLETED:passed (premature) |
| `moderate-2-mdn-web-api-detail` | 0.33 | navigate ✓ → snapshot ✓ → click ✓ → click on `uid=1_20` → 2 same-shape `interact{click, uid}` parse-fails → REFLECT → continued retry → MAX_TOOL_ROUNDS |
| `journey-8-help-center` | 0.25 | 7 turns of progress → scroll-action parse-fail loop → REFLECT → continued retry |

**Finding 3.A**: `calibration-1-oracle-plan` reveals a **detector
limitation**. The trace has 5 turns of THOUGHTs, each acknowledging
"the previous action failed", with 0 visible tool_call events and 0
REFLECT chunks. Mechanism: each malformed envelope had a
**slightly different shape** (model's THOUGHTs say "I will try to
simplify", "I will use the URL as a direct string", "I will use the
URL as a key" — varying its strategy each attempt). The detector
requires `same stepId + same shapeHash` for streak accumulation. With
varied shapes, every attempt resets the streak to 1, so the 2nd-strike
threshold is never reached. **Same-shape requirement is too strict
for "vary-each-attempt" rejection patterns.**

This is a **harness-r4 detector-tuning hook**: relax shape-matching
to `same-stepId-any-rejection-Nrelax` for a softer same-step trigger
(threshold 3, equivalent to DOOM_LOOP_THRESHOLD), keeping the
existing strict same-shape detector at threshold 2 for the
high-confidence path. Two-tier detector ladder.

**Finding 3.B**: the Pro 3 plans themselves were not visibly flawed
in the 4 sampled traces. The plans got the model into the right
URL/page/UID, but the model couldn't execute the next-shape action
correctly. Plan quality is NOT the bottleneck; envelope-formatting
under the plan IS.

### Thread 4 — What does action=replace require that action=remove didn't?

Calibration-5 (the only PLAN_UPDATE emission) verbatim turn-7 reasoning:

> "The `REFLECT` directive has been triggered because the `interact`
> tool call for navigation failed twice in a row. I must now use
> `PLAN_UPDATE` to correct the plan. **Since the navigation step
> itself is failing due to a persistent schema error**, I cannot
> proceed with the original plan. I will remove the failing
> navigation step and report **the inability to complete the task
> due to tool constraints**."

Comparison: moderate-2-oracle-plan turn-9 (REFLECT fires, model
ignores):

> "The click action on uid=1_20 continues to fail with a schema
> error, indicating a **persistent issue with how the `interact`
> tool accepts the `uid` argument**. Since the element is a
> button/expandable element..."

Calibration-1-oracle-plan turn-3:

> "Since the tool definition is strict, I will assume the **tool
> expects the URL as a direct string argument**, not nested under a
> specific key, or that the **tool call itself is malformed**."

**Finding 4.A — causal misattribution under repeated failure**: in
all 4 inspected traces, the model's reasoning externalizes blame to
the tool / environment ("tool constraints", "tool schema flawed",
"environment can't process") rather than recognizing self-error
("MY envelope is malformed, let me reshape it"). The model has
reasoned itself into a "the tool is broken" framing by the time
REFLECT arrives. From that frame:

- `action=remove` (surrender) is consistent — "the tool can't do
  this, drop the step".
- `action=replace` (corrected step) is **inconsistent** — "the
  tool is the problem, so a different step won't help either".
- `action=insert` (prerequisite) is also inconsistent.

The capability gap is NOT "model can't format PLAN_UPDATE" (calibration-5
proves the format is intact) — it's **"model has misattributed the
error source, so the recovery shape that requires self-attribution is
unreachable"**. Gemma's reasoning template defaults to environment-
blame under repeated failure; the recovery shape requires
self-blame.

**Finding 4.B**: this is a teaching target for R12 distillation. Pro
3 teacher trajectories should explicitly model the
self-attribution-then-recovery cadence: "the previous envelope was
malformed in shape X; the corrected envelope is Y" → then emit the
corrected ACTION or PLAN_UPDATE action=replace with corrected step.
Without seeing this pattern in teacher data, gemma's prior bias
(externalize blame) dominates.
