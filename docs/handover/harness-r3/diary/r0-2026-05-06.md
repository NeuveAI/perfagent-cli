**Detector design** (`packages/local-agent/src/tool-loop.ts`):

- Constants colocated with `DOOM_LOOP_THRESHOLD = 3`:
  - `REFLECT_INJECTION_THRESHOLD = 2` (strictly less than doom-loop so injection precedes abort)
  - `REFLECT_DIRECTIVE_TEXT` (single-source string; same wording in
    chunk-update + observation prefix)
- New `RejectionFingerprint` interface `{ stepId, shapeHash, kind: "parse-fail" | "tool-error" }`.
- `recentRejections[]` sliding window capped at `DOOM_LOOP_THRESHOLD`. Streak
  resets when shape changes, on PLAN_UPDATE / STEP_DONE (forward progress),
  or on a successful (non-error) tool call.
- `lastSeenStepId` tracks the most-recent envelope's `stepId` so a
  parse-fail with no extractable stepId attributes the rejection to the
  step being worked on.
- Critical behavioral change at the parse-failure branch (`tool-loop.ts:208`):
  pre-r3 the loop aborted on the first `SchemaError` ("non-schema-valid
  agent output. Aborting run."); post-r3 the loop:
  1. Feeds the parse failure back as `<observation>(parse failure: ...)</observation>`
  2. Tracks the rejection under `stepId + shapeHash` (200-char normalized
     prefix of envelope content)
  3. On the **second same-shape parse-fail** prepends a `<observation>REFLECT: ...</observation>`
     to the next observation message AND surfaces a UI chunk
     `[Local agent: REFLECT: ...]`
  4. On the **third same-shape parse-fail** aborts via the existing
     doom-loop seam with a refreshed message: `non-schema-valid agent
     output 3× in a row. Aborting run.`

**Tool-error path** (Action envelope parses, but `mcpBridge.callTool`
returns `isError=true`):

- `shapeHash = "tool:" + functionName + ":" + argsHash` so two consecutive
  same-tool+same-args rejections collapse into a single streak.
- Existing doom-loop detector (3 identical consecutive ACTION envelopes)
  unchanged. The new `REFLECT_INJECTION_THRESHOLD=2` fires one step
  earlier and prepends the directive to the observation; the doom-loop
  abort still fires at threshold=3 if the model can't recover.

### Harness-r4 candidate (from P2): THOUGHT-only loop detector

**Trigger condition**: track consecutive THOUGHT envelopes on the same
`stepId` without an intervening ACTION / STEP_DONE / PLAN_UPDATE
envelope. Reset on any non-THOUGHT envelope, on stepId change, or on
RUN_COMPLETED.

**Proposed thresholds** (symmetric with the existing detector ladder
`REFLECT_INJECTION_THRESHOLD = 2` < `DOOM_LOOP_THRESHOLD = 3`):

- `THOUGHT_REFLECT_THRESHOLD = 5` — after 5 consecutive same-stepId
  THOUGHTs, inject `<observation>The plan is stuck in deliberation.
  Emit ACTION (try the next concrete tool call) or PLAN_UPDATE (revise
  the step). Continued THOUGHT-only output for one more turn will
  abort.</observation>` into the next observation, AND surface a UI
  chunk `[Local agent: thought-only loop detected — emit ACTION or
  PLAN_UPDATE]`.
- `THOUGHT_LOOP_ABORT_THRESHOLD = 6` — after 6 consecutive same-stepId
  THOUGHTs without recovery, abort via the existing doom-loop seam
  ("Aborting to avoid wasted cycles"). Bounded at 6 to preserve
  budget — reaching 6 means the model burned 6 of 15 MAX_TOOL_ROUNDS
  on reasoning alone.

**Threshold rationale**: 5 consecutive same-stepId THOUGHTs is the
incidence-rate floor where the pattern becomes pathological in
practice (see incidence table below). Below 5, the model is doing
legitimate multi-step reasoning. At 5 the gemma stack has emitted
roughly half a turn-budget on reasoning alone — strong signal the
model is stuck. The 6th turn is the abort guard so total reasoning
overhead is bounded.

**File pointer for harness-r4**:
`packages/local-agent/src/tool-loop.ts` Thought branch (currently lines
245–258 in HEAD `76d9c8f7` — emits `agent_thought_chunk` + observation,
adjacent to the new `lastSeenStepId = envelope.stepId` mutation). Add
parallel `recentThoughtCount` counter; reset in every non-Thought
branch the way `recentRejections` resets on PLAN_UPDATE / STEP_DONE.
Mirror in `packages/evals/src/runners/gemini-react-loop.ts` lines

`REFLECT_INJECTION_THRESHOLD` and `GEMINI_REACT_REFLECT_INJECTION_THRESHOLD`
respectively.

#### Incidence script (archived inline for reproducibility)

```bash
# THOUGHT-only loop incidence: count tasks where ≥ 5 consecutive turns
# produced agent_message events only (no tool_call between them) on the
# same stepId. Run from repo root.
for sweep in pin-1 pin-2; do
  for runner in gemma-react gemini-react gemma-oracle-plan; do
    dir="packages/evals/evals/traces/wave-harness-r2-$sweep"
    for f in "$dir"/${runner}__*.ndjson; do
      [ -f "$f" ] || continue
      task=$(basename "$f" .ndjson)
      runlen=$(python3 -c "
import json
turns_with_tool = set()
agent_message_turns = set()
with open('$f') as h:
    for line in h:
        try: ev = json.loads(line)
        except Exception: continue
        t = ev.get('turn')
        if t is None: continue
        if ev.get('type') == 'tool_call': turns_with_tool.add(t)
        elif ev.get('type') == 'agent_message': agent_message_turns.add(t)
turns = sorted(set(agent_message_turns) | set(turns_with_tool))
maxrun = 0
cur = 0
for t in turns:
    if t in agent_message_turns and t not in turns_with_tool:
        cur += 1
        if cur > maxrun: maxrun = cur
    else:
        cur = 0
print(maxrun)
")
      if [ "$runlen" -ge 5 ]; then
        echo "$sweep $runner $task max-thought-run=$runlen"
      fi
    done
  done
done
```

Note: the script approximates "same-stepId" via "any agent_message turn
with no tool_call in same turn". For a precise harness-r4 implementation
the detector would track `stepId` from the last-seen envelope (the way
P1's `lastSeenStepId` does) rather than turn-bookkeeping in the trace.
The incidence rate is robust to this approximation because gemma's
THOUGHT-loops happen within a single stepId in practice (the model
doesn't bounce between steps mid-loop) — verified by spot-check of
`gemma-react__journey-6-media-streaming.ndjson` pin-2.
